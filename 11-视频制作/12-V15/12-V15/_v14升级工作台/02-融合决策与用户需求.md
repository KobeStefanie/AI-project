## 二、用户明确拍板的决策

1. **双轨**：B 轨为主（镜头N 无秒数），A 轨只给一镜到底（时间戳只做因果段落划分）。两轨都禁止「第 N 秒做什么动作」级配方。
2. **融合深度**：器官移植 —— 保留我们的 6 agent / ~指令集 / assets+outputs 目录 / 175 位色卡 / 编剧流程 / 模型无关时长；移植他们的镜头表中间层、五张工艺卡、retake、围栏四块、查病式审核。

## 三、用户的定位修正（重要，影响档位设计）

- **主要做：精品微电影 + MV**。短剧/漫剧是以后的延展方向（架构要兼容但不是主场）。
- 含义：微电影 = 他们的「电影级」= 走**全装**的严谨度（完整镜头表、完整审核）；MV 按体量选档；不要因为 Lite 更轻就整体采 Lite —— Lite 只在特定条目上采（见下）。

## 四、用户点名必须做好的四件事

1. **台账（continuity ledger）不要遗漏** —— 他们的归档做得好，全套移植（12 项状态机 / 六块 ledger / 缝审计八查 / 线头 [开]/[关闭]）。
2. **素材对应要方便** —— 用户要拿着产出去生成素材：每条提示词上传哪几张图、图叫什么名、存在哪里，必须一眼看清（→ 条头上传清单五列 + reference-index + PNG 存放位置约定）。
3. **输入位置要明确** —— 想法/剧本/参考一开始放哪里，要在开场就告诉用户（V13 已有 input/选题|剧本|参考，保留并在新手引导里讲清）。
4. **新手引导** —— 版本迭代快，用户担心自己和其他用户不会用。KAIKAI 开场之后、新创作任务开始时要有一段新手引导（放什么→问什么→产出什么→拿去哪生成→翻车怎么办，一条龙讲清）。

## 五、用户对可靠性的要求

- **API 容易中断，要有应对，不希望有缺漏** → 采纳 3.0 的「文件是记忆，Session 不是」：
  - 所有跨窗口有价值的结论当轮落盘（判据：这个窗口现在被关掉，这条信息会丢吗？）
  - 升级工作本身也照此办：深读提炼、决策记录全部落 `_v14升级工作台/`
  - V14 运行时机制：agent 每完成一个实质产物立即落盘；制片人断点续跑按「产物文件在不在」判断位置，不依赖会话记忆
  - Resumable Subagents（agentId）保留为便利层，但**文件才是事实层** —— agentId 失效时从文件恢复，不算事故

## 六、色彩锚升级（用户补充，V13 融合得不够好）

现状问题：用户点名导演 → 用色卡；不点名 → agent 即兴写形容词。**中间缺一档**。
V14 规则（三级）：
1. 用户点名导演 → 直接取该导演色卡（现有逻辑）
2. 用户不点名 → **agent 必须先查 `director-index.md`**，根据题材/平台/受众/对标爆款从 175 位里选 2–3 位候选，附一句话理由推荐给用户认领（对应 3.0 director-grill 的「风格锚定+上网研究」精神：主动定锚，不等用户开口）
3. 用户明确说「不要导演锚，自由创作」→ 才走自由创作，且写入 settings 防反复追问

## 七、BGM 冲突的裁决（已定，有官方佐证）

- 3.0 完整版：BGM 写进提示词。3.0 **Lite 版：「BGM 默认后期铺、提示词只写『无背景音乐』」= 与我们 V13 完全一致**。
- V14 裁决：BGM 一律「无背景音乐」+ 音乐总监后期铺（我们/Lite 路线）；`content_type=mv` 时例外，允许按 3.0 句式写 BGM 指令（风格+乐器+节奏+进退时机，禁点歌名艺人）。
- 吸收他们的技术理由：**不写 BGM 指令的条，模型会自作主张塞配乐——沉默也要写出来**。
- 台词/音效/环境声三要素句式**全盘移植**（我们原来只笼统写「音效」）。
