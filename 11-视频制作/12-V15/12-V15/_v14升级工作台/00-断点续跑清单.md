## 容灾纪律（本次升级的教训，写进制度）

1. **不派长任务 fork**：用户 API 环境不稳，fork 存活率低。改为主线顺序做，每步一个 Write/Edit 即落盘
2. **不信进度报告，只信 grep**：任何「已完成」都要用自检脚本验证
3. **清单先行**：开工前先写这份清单，中断后不用重新推理做到哪了
4. **深读类工作必须边读边落盘**：不攒到最后一次写（第一次深读 2 就是攒着写，502 全丢）
5. **落盘动作与勾选动作必须紧邻**：不允许「先勾选、稍后写」，也不允许凭记忆补写细节——细节只能从 Read 结果里抄。理由见上方「诚实性事故记录」：两条假记录都是「记忆里以为做了」+「细节自行填充」的产物，而不是故意撒谎；只要允许记忆参与，压缩或断联之后就一定会掺进编造。
6. **Edit 前必先 Read 目标行**：逐字复制 old_string，不凭印象猜缩进与前缀（此前有 2 次 Edit 因猜写失败）。
7. **不用 Bash 跑分类器类命令**：本环境 Bash 工具会触发 `claude-opus-4-8 temporarily unavailable (timed out)`。改用 Grep / Read / Glob / Write / Edit，实测连续 13 次调用零失败。自检脚本交给用户自己粘进终端跑。
9. **Edit 前必须先 Read 目标行段，old_string 逐字抄自 Read 结果**（2026-09-10 修订，原写「只认单文件 grep」，理由已更正）：本次升级最大的消耗不是工具错乱，而是**我自己幻读**——生成一段不存在的文件内容并当成读到的，然后据此动手改。机器扫描（`scan-degenerate.py` → `scan-report.txt`，129 个 md）证明我报过的十来处「文件坏了」一处都不存在。所以：**「我觉得这里坏了」不是证据**，判断顺序固定为「机器扫描 → 单文件 grep 特征短串 → Read 目标行段 → 才允许 Edit」。另：修断链时**优先补生产方，而不是删消费方**——消费方多处在正当使用某个字段，说明该能力是有意引入的，删掉等于砍功能（G8-2 的「摄影三件套」就是这样保下来的）。
10. **「改文件的 Edit」与「登记该修改的 Edit」不得同批并发发出**（2026-09-10 新增）：本次两次犯规，结果是登记先落盘、改动其实失败，产出假完成记录。顺序必须是「改 → 看到成功结果 → 再登记」。
11. **上下文压缩会重置 harness 的「已 Read」记录**（2026-09-10 实测新增）：压缩前读过不算。压缩后对任何文件 Edit，必须在新窗口内重新 Read 目标行段，否则一律被 `File has not been read yet` 挡下（本次连续被挡 5 次才发现）。接手的人第一个动作就是把要改的文件重新 Read 一遍。
12. **判断退化/损坏一律先跑机器扫描**（2026-09-10 新增）：`cd 到 11-V14` 后 `python -X utf8 '_v14升级工作台/scan-degenerate.py'`，结果落 `_v14升级工作台/scan-report.txt`（不走 stdout，因为 PowerShell 会话结束会 reset cwd、长 stdout 也不便复核）。七类检测：markdown 标题重复 / `[章节名]` 重复 / 同行 ≥5 次 / `{{描述…}}` 占位符 / 连续表分隔行 / 表内整行与首列重复 / 自指引用。
